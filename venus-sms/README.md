# Venus SMS result workflow

Independent Venus program for the existing mock SMS Relay. This program does not
replace or modify the previously successful native HTTP POST REX request.
No provider credential is accepted or required.

Application state has exactly two fields: `message_id` and `status`. Venus adds
its own framework branch counter (manifest calls this the discriminator).
Phone numbers, message body, and Relay URL are not application state fields.
They are public transaction inputs, so use dummy data only.

`start(relay_url, payload)` sends a single asynchronous JSON POST. The Relay URL
is supplied at invocation; no temporary hostname is compiled into the program.
`receive_delivery(report)` reads a successful raw REX response, parses the Relay
JSON schema, requires a nonempty message ID and `status == delivered`, and saves
the two fields. Malformed or unsuccessful responses fail instead of being counted
as successful. This remains a mock-only prototype.

The HTTP operation explicitly sets `request_delay_ms: 5000u64` (milliseconds)
and `validators_per_duty: 1u32`. In official 0.18.1, omitting these options uses
300ms and five validators. REX `Timeout` returns `ProgramError::Custom(5000)`
(hex `0x1388`) rather than `InvalidAccountData`; the numeric error code is an
application identifier, not the measured request duration. State and callback
accounts are unchanged. A regression test covers reports with 300ms and 5000ms
timeouts.

`read_result()` is a separate control invocation. Venus preflight loads the
persisted state, and the function emits the two values as `SMS_STATE ...` in the
transaction logs. It does not send another HTTP request. It is a transaction,
not a free read-only RPC. A workflow account can also be read with the official
account RPC and decoded with the official `rialo_venus::read_from_storage` format.

## Official implementation basis

- Official `venus/multi-http-post/src/lib.rs`: `AFTER [http_post ...] CALL`,
  `RexReport::outputs`, `RexOutput::Success`, `response.as_raw()`, and state assignment.
  https://raw.githubusercontent.com/SubzeroLabs/rialo-examples/main/venus/multi-http-post/src/lib.rs
- `rialo-venus-dsl 0.18.1`,
  `src/generate/workflow/implementation_module/program_implementation.rs`:
  `program_lifecycle_methods` generates preflight reading and postflight writing.
- `rialo-venus 0.18.1`, `src/lib.rs`: `read_from_storage` / `write_to_storage`.
- `rialo-build-lib 0.18.1`, `src/build_script.rs`:
  `setup_polkavm_artifact_build().program_path("..").run()` builds the artifact;
  `RIALO_BUILD_ARTIFACT_FILE` is a filename relative to `OUT_DIR`.
- Installed official CLI `rialo 0.18.1-2e1fdefe31cc`:
  `program deploy-venus`, `program invoke`, `transaction`, `get-workflow-lineage`.

All Rialo dependencies are pinned to `=0.18.1`; `Cargo.lock` captures the resolved
dependencies. The manifest and WIT are generated by the official macro, not
handwritten. The host tests exercise JSON decoding; DevNet verification is
required separately to establish actual handler dispatch and persistence.

## Build and test

```sh
cd rialo-agentic-edge-sms-gateway/venus-sms
cargo test -p venus-sms --features implementation --locked
cargo build --manifest-path artifact/Cargo.toml --locked
```

The installed Rialo Rust toolchain is used by the official artifact build helper.
Generated PolkaVM output is under `target/rialo-build/venus-sms-riscv/`.

## DevNet only

Deploy a new program using `rialo --no-setup --network devnet --json client program
deploy-venus .`. Invoke `start` with the resulting program ID, `--program-dir .`,
and manifest parameters `workflow_pda_slug` (32-byte hex), `relay_url` (current
HTTPS endpoint), and `payload` (JSON string with `to`, `from`, `message`).
Reuse the same program ID and slug for `read_result`. Do not replay `start` to
read a result. Keep the Relay and tunnel running until the callback finishes.

Check the initiating transaction's lineage for the handler transaction. Compare
the REX response with both the handler's state log and a separate `read_result`
transaction. Mock `delivered` does not mean that any real SMS was sent.

## 5000ms verification (2026-09-24)

Local checks passed: three Venus tests, eight Relay tests, and artifact build.
The generated manifest remained byte-for-byte identical. A new DevNet deployment
and exactly one `start` invocation succeeded. REX account reads confirmed 5000ms
and one validator, but no REX report or handler was observed. At block 20250855,
after the subscription's active commit range ended at 20250086, workflow state
still contained empty strings. No `read_result` transaction or second `start`
was sent. This run is BLOCKED, not a successful delivery or an observed Timeout.
The reason for the missing report remains unconfirmed.
